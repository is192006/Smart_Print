\chapter{Project Selection Phase}

\section{Software Bid}

\subsection*{Problem Being Addressed}
College printing shops on campus are operated as a walk-in, paper-driven service. A student or faculty member must carry a document (typically on a USB drive or by emailing it to the shop's system), physically wait at the counter while the shop staff opens, formats, and prints it, and pay in cash on collection. During peak hours -- before assignment deadlines or exams -- this produces long physical queues, no visibility into how many jobs are ahead of a given request, and no record of what was printed, when, or at what price. Shop staff have no digital worklist and must track pending jobs manually.

\subsection*{Proposed Solution}
SmartPrint is a web-based printing-management platform that lets Students and Faculty upload a document, choose print settings (paper size, colour mode, sides, copies, page range, and an optional finishing option such as spiral binding), and place an order against a specific print shop. The shop's price is resolved automatically from that shop's active pricing rules at the moment of ordering. Payment is completed online (through a payment abstraction that can later be connected to a real gateway), after which the order is placed into that shop's first-in-first-out printing queue. Shop Staff work from a queue dashboard that shows exactly which order to print next, and Admin users oversee shops, staff, and pricing across the institution.

\subsection*{Project Objectives}
\begin{itemize}[leftmargin=0.7cm]
  \item Remove the need for a student/faculty member to be physically present while a document is queued for printing.
  \item Give every party (student, staff, admin) a live, structured view of order status instead of an informal physical line.
  \item Make per-page and per-finishing pricing transparent and centrally configurable per shop.
  \item Support the free-printing entitlement that CSE faculty already have at the departmental printer, enforced in software rather than trusted to memory.
  \item Provide a clean cancellation/refund path so a student is not charged for an order the shop never started printing.
\end{itemize}

\subsection*{Target Users}
Four roles exist in the system: \textbf{Student} (self-registers, pays for printing), \textbf{Faculty} (provisioned by an Admin, can print for free at the CSE department printer), \textbf{Shop Staff} (provisioned by an Admin and assigned to exactly one print shop, operates that shop's queue and pricing), and \textbf{Admin} (manages shops, staff, faculty accounts, and can view every order).

\subsection*{Major Functionality}
Document upload and validation; shop and pricing/finishing-rule browsing; order placement with server-computed pricing; online payment initiation and confirmation; a FIFO print queue per shop; order cancellation and refund requests; queue processing (start-next, mark-ready, collect) by shop staff; and administrative management of shops, staff/faculty accounts, and pricing.

\subsection*{Expected Benefits}
Reduced physical waiting time for students and faculty, a clear audit trail of every order (status history, payments, refunds), fairer queue handling because slot order is determined by system timestamp rather than who can shout loudest at the counter, and centralised, auditable pricing instead of ad-hoc cash pricing at each shop.

\subsection*{Scope and Constraints}
The current implementation targets a single institution with multiple independently operated print shops. Payment is processed through a mock/simulated payment provider suitable for a development and evaluation environment (module boundaries are written so a real gateway can be substituted later). Only PDF and common office/image document types are supported for upload. Queue ordering is strictly first-in-first-out by the time an order is confirmed for printing; no priority-weighting scheme is implemented in the current codebase.

\section{Project Overview}

\subsection*{Existing Printing Problem}
The manual, walk-in printing workflow described above scales poorly with the volume of requests around deadlines, gives students no way to plan their visit around queue length, and leaves shop staff without any structured way to track outstanding work across multiple concurrent orders.

\subsection*{Motivation}
A digital, queue-based system converts an unmanaged physical line into an ordered, trackable pipeline: submission, payment, queueing, printing, and collection each become an explicit, timestamped state transition that both the customer and the shop can see.

\subsection*{Proposed SmartPrint Solution}
SmartPrint is implemented as a two-tier web application: a React/TypeScript single-page frontend and a Node.js/Express/TypeScript REST API backend, backed by a PostgreSQL database accessed through the Prisma ORM. Authentication uses JSON Web Tokens issued on login, with role-based route guards enforced on both the frontend (route-level redirects) and backend (middleware-level authorization checks on every protected endpoint).

\subsection*{System Workflow}
A Student or Faculty user registers/logs in, uploads a document, selects a shop and print options, and places an order. The backend resolves the correct price from that shop's currently effective pricing and finishing rules (never trusting a client-supplied price) and creates the order in a \texttt{PLACED} state. If payment is required, the user initiates and confirms payment; on a successful confirmation the order becomes \texttt{PAYMENT\_CONFIRMED} and is atomically inserted into that shop's FIFO queue as \texttt{QUEUED}. Faculty ordering at the dedicated CSE faculty shop skip payment entirely -- their order total is computed as zero and they are queued immediately. Shop Staff start the next waiting order (moving it to \texttt{PRINTING}), mark it complete (\texttt{READY}), and mark it collected (\texttt{COLLECTED}) once the customer has picked it up. A student/faculty user may cancel an order any time before printing has started, and may request a refund once a paid order has been cancelled; an Admin settles that refund request.

\subsection*{Major Modules}
\begin{itemize}[leftmargin=0.7cm]
  \item \textbf{Identity \& Access} -- registration, login, JWT issuance, password reset, role-based authorization.
  \item \textbf{Document Management} -- upload, storage, metadata (file type, size, page count), listing, viewing/downloading, and deletion.
  \item \textbf{Shop \& Pricing} -- shop directory, per-shop pricing rules (print type / paper size / sides), and per-shop finishing rules, each with an effective-date window.
  \item \textbf{Order Management} -- order creation with server-resolved pricing, cancellation, and order-status history.
  \item \textbf{Payments \& Refunds} -- payment initiation/confirmation against a mock payment provider, and refund request/processing tied to cancelled, paid orders.
  \item \textbf{Print Queue} -- a strict FIFO queue per shop, with start-next / mark-ready / collect operations for Shop Staff and Admin.
  \item \textbf{Administration} -- shop creation/updates, Shop Staff and Faculty account provisioning and shop assignment, and system-wide order visibility.
\end{itemize}

\subsection*{Users / Roles}
Student, Faculty, Shop Staff, Admin -- exactly the four roles defined in the system's \texttt{UserRole} enumeration, each gated by dedicated backend authorization middleware and dedicated frontend routes.

\subsection*{Technology / Architecture}
\textbf{Frontend:} React 19 with TypeScript, Vite, and React Router. \textbf{Backend:} Node.js with Express and TypeScript, organised into route/controller/service layers. \textbf{Database:} PostgreSQL, managed through Prisma ORM migrations. \textbf{Auth:} JSON Web Tokens with bcrypt-hashed passwords. \textbf{File handling:} Multer for uploads, with per-type document processors (PDF, Word, Excel, PowerPoint, image formats) used to extract page counts where possible. \textbf{Testing:} Jest for backend integration tests, Vitest for frontend unit tests. \textbf{Deployment:} Dockerfiles are provided for both the frontend and backend services.

\subsection*{Expected Outcome}
A working, role-correct printing-management platform in which every order's lifecycle -- placement, pricing, payment, queueing, printing, collection, or cancellation/refund -- is fully traceable, and in which shop staff and administrators operate from live, structured views rather than an informal physical queue.

\subsection{Use Case Scenarios}

\textbf{Scenario 1 -- Standard Paid Order.} A Student uploads a document, places an order at a shop that is accepting orders, pays successfully, and the order is queued, printed, marked ready, and collected in sequence.

\textbf{Scenario 2 -- Free Faculty Order.} A Faculty member places an order at the CSE faculty shop; the order total is zero, no payment step occurs, and the order is queued immediately.

\textbf{Scenario 3 -- Cancellation and Refund.} A Student cancels a \texttt{QUEUED} order before it starts printing, then requests a refund of the successful payment already made; an Admin later processes that refund.

\textbf{Scenario 4 -- Queue Processing.} A Shop Staff member starts the next waiting order at their shop (blocked if another order is already printing), marks it ready once printed, and later marks it collected.

\section{Software Requirement Specification in IEEE Format}

\subsection{Introduction}

\subsubsection*{Purpose}
This Software Requirements Specification describes the functional and non-functional requirements of SmartPrint, a college printing-management system, as actually implemented at the time of the mid-semester evaluation.

\subsubsection*{Scope}
SmartPrint allows Students and Faculty to upload documents and place print orders against a chosen shop, pay for those orders, track and cancel them, and request refunds; it allows Shop Staff to operate their shop's print queue and pricing; and it allows an Admin to manage shops, staff/faculty accounts, and pricing, and to view all orders. The system excludes real payment-gateway integration (a mock provider is used), priority-based queue scheduling, and any reprint workflow -- none of these exist in the current codebase.

\subsubsection*{Definitions, Acronyms and Abbreviations}
\textbf{FIFO} -- First-In-First-Out. \textbf{JWT} -- JSON Web Token. \textbf{ORM} -- Object-Relational Mapper. \textbf{CSE\_FACULTY shop} -- the departmental print shop at which Faculty printing is free.

\subsubsection*{Intended Audience}
The development team, the course faculty evaluating this submission, and future maintainers of the SmartPrint codebase.

\subsubsection*{References}
IEEE Std 830-1998, Recommended Practice for Software Requirements Specifications; the SmartPrint source repository (Prisma schema, Express route/controller/service layers, React frontend).

\subsection{Overall Description}

\subsubsection*{Product Perspective}
SmartPrint is a new, self-contained two-tier web application: a React/TypeScript frontend consuming a REST API served by a Node.js/Express/TypeScript backend, backed by a PostgreSQL database.

\subsubsection*{Product Functions}
Document upload and management; shop and pricing browsing; order placement with server-resolved pricing; payment initiation and confirmation; FIFO queue processing; order tracking, cancellation, and refunds; and administrative management of shops, staff, faculty accounts, and pricing.

\subsubsection*{User Classes and Characteristics}
\textbf{Student} -- self-registers, uploads documents, pays for print orders. \textbf{Faculty} -- provisioned by Admin, prints for free at the CSE department shop, pays at other shops like a student. \textbf{Shop Staff} -- provisioned by Admin, assigned to exactly one shop, operates that shop's queue and pricing. \textbf{Admin} -- manages shops, staff, faculty accounts, pricing, and has visibility over all orders.

\subsubsection*{Operating Environment}
The backend runs as a Node.js service against a PostgreSQL database managed through Prisma migrations; the frontend is a static single-page application built with Vite and served independently. Dockerfiles are provided for both services.

\subsubsection*{Design and Implementation Constraints}
All prices are resolved server-side from a shop's currently effective pricing/finishing rules; a client-supplied price is never trusted. An order can enter a shop's queue only after a successful payment, except for the CSE Faculty free-printing entitlement. Only one order may be actively printing per shop at any time.

\subsubsection*{Assumptions and Dependencies}
The payment provider used in the current build is a mock/simulated provider intended for development and testing; production use would require substituting a real gateway behind the same interface.

\chapter{Feasibility Report}

\section{Technical Feasibility}
SmartPrint is built entirely on mature, freely available, well-documented technologies: React with TypeScript on the frontend, Node.js/Express with TypeScript on the backend, PostgreSQL managed through the Prisma ORM, JSON Web Tokens for authentication, and bcrypt for password hashing. None of these require specialised hardware, proprietary licensing, or research-level effort to use correctly. The team already has working knowledge of JavaScript/TypeScript and REST API design from prior coursework, and the remaining pieces (Prisma migrations, JWT-based auth, role-based middleware) are standard, well-documented patterns rather than novel engineering. The codebase already demonstrates the harder integration points working end-to-end -- transactional payment-to-queue insertion, per-shop staff access checks re-derived from the database rather than trusted client input, and price snapshotting at order time -- which substantially de-risks the remaining feature work for this evaluation period. The system is technically feasible to build, test, and demonstrate within the semester timeline.

\section{Economic Feasibility}
Every component in the stack -- Node.js, PostgreSQL, React, Prisma -- is open-source and free to use for development and academic deployment. The payment layer currently uses a mock/simulated provider, avoiding any transaction-fee cost during development; a production deployment would incur only the standard, low per-transaction fee of whichever real payment gateway is eventually integrated behind the existing payment interface. Hosting costs for a single-institution deployment (one small database instance and one small application server) are modest and fall well within typical academic or small-institutional budgets. No specialised or expensive infrastructure is required.

\section{Operational Feasibility}
The workflow SmartPrint automates -- upload, price, pay, queue, print, collect -- maps directly onto the physical counter workflow shop staff already perform, so the learning curve for Shop Staff is limited to using a queue dashboard instead of a mental or paper list. Students and Faculty already use web and mobile applications daily, so the ordering flow requires no special training. Role-based access (Student/Faculty self-service, Shop Staff shop-scoped operations, Admin system-wide oversight) matches the real organisational structure of a college with multiple independently staffed print shops, so adoption does not require restructuring how the shops are run. The existing backend integration test suite (thirteen test files covering authentication, documents, orders, payments, pricing, queue, and refunds) and frontend unit test suite give reasonable confidence that core workflows behave correctly before a real deployment.

\section{Schedule Feasibility}
The core domain -- authentication, document upload, shop/pricing management, order placement with server-side pricing, payment simulation, FIFO queueing, and refund handling -- is already implemented and covered by tests, as verified directly against the repository for this report. The remaining work toward a full submission is incremental: replacing the mock payment provider with a real gateway, and polishing the administrative reporting views. Given that the foundational, highest-risk pieces (transactional order/payment/queue consistency, role-scoped shop access) are already working, the project is on schedule to be completed and demonstrated within the remaining weeks of the semester.
